# 1.0.4 第二轮逻辑复查

在 1.0.3 本机卡死修复推送后，再次对核心策略、插件 Java／Kotlin、浏览器辅助脚本、构建／发布脚本进行静态筛查，沿界面入口、后台请求、原生回调与停止路径复核共享锁、同步等待、取消门禁、所有权与延迟任务。这里记录的是代码检查与受控回归发现的问题；1.0.3 的真实窗口回调现场证据另见 [本机定位记录](DEVICE_FREEZE_FIX_1.0.3.md)。

## 修复的等待链

- **视频原生命令**：画面释放已在后台，但后台 `tick` 仍持有视频会话监视器查询 mpv 属性，界面切换／销毁需要同一监视器。原生查询、命令和播放器构造现在在独立后台锁下运行；界面状态只在短锁内快照或发布。销毁等待正在执行的原生命令及所有画面释放屏障，加载失败和被取消的新播放器也在后台销毁。鼠标位置查询移出会话锁，防止 Windows 输入回调反向等待。
- **后台缓存撤销**：仅判断 AWT 不够。后台撤销、注册时清理过期条目和停止可能持有传输锁等待磁盘缓存，界面随后等待传输锁。持有传输监视器的磁盘维护现在也转交串行维护执行器。缓存容量、已用字节和修订号通过 volatile 元数据读取，无需等待文件 I/O 的监视器。
- **Apple Music PCM／浏览器关闭**：关闭 PCM 源会直接等待浏览器退出、管道写入完成、临时档案删除及 PCM 读取监视器。现在立即标记退休，在后台先关闭浏览器以解除读取，再等待读取退出并清零缓存。已退休的新读取在取得 PCM 监视器前就失败，正在读取的任务也不能返回退休后的 PCM。取消时不再向浏览器追加暂停请求。浏览器只关闭一次。
- **歌曲身份事务**：歌曲事务持锁写文件，界面和视频读取身份、关闭存储也拿同一把锁。身份读取现在使用仅包含已提交记录的不可变快照；关闭只撤下快照并退休持久封面。事务在提交／发布时检查关闭状态，无法恢复已关闭的存储。保存至宿主歌单的磁盘步骤也移出插件生命周期锁。
- **持久封面与播放提交**：读取封面、补写封面或准备占位文件原来在歌曲会话锁内完成，界面清理可能等磁盘。文件步骤现在位于状态锁之外，封面任务提交前检查请求／账户／代次，播放任务文件完成后重新检查有效性。封面定时器先在锁外读磁盘，再核对选中绑定；调度只读取已知封面状态。持久封面退休只撤销预约，不等磁盘锁或删除保留的文件。在线提交的磁盘步骤也移出播放运行时监视器，最终入队前重新检查运行时／账号。
- **BASS 暂存文件**：宿主释放原生句柄后的暂存文件删除移出流所有权锁，避免慢文件删除让工厂撤销／关闭一起等待；原生句柄仍由宿主管理。
- **旧队列与临时封面**：延迟歌单、旧播放会话的封面替换移出队列／会话锁；旧单曲准备与运行时提交同样拆开文件准备和最终发布。临时封面的清理和删除在最多两个后台工作线程上执行，逻辑退休立即返回；延迟清理按封面修订号检查，不能擦掉重播刚写入的新图像。工作线程空闲后退出。

## 验证

新增 `VideoControlResponsivenessTest`、`AppleMusicRetirementTest`、`SavedStorageResponsivenessTest`，扩展 `CacheUiResponsivenessTest`。测试让实际生产方法遇到忽略中断的原生查询／加载／销毁、CDP 读取／浏览器清理、歌曲事务及封面监视器阻塞，验证 AWT 哨兵和关闭返回、旧任务发布门禁、读取／销毁顺序及单次资源释放。测试不需要用户账号或真实平台媒体。

视频失败同时递增代次并取消未完成请求。后台加载排队期间发生失败时，旧任务不能重新创建播放器、恢复已失败的视频状态；视频控制回归对此建立了受控双加载场景。

原有 Apple 队列／PCM 检查现在等待实际资源退休完成，再核对一次关闭；导航不关闭已转交宿主的 PCM 所有权规则保留。原有批量歌单、封面读取／重试／快速切换／重启、实际宿主标签解析、视频会话与原生离屏渲染继续验证。

完整清单为 102 个入口与 35 个 `java.base` 变体。默认不运行前台鼠标、屏幕采样和视频帧率测试。静态复核和受控回归不能证明所有设备、远端服务及驱动场景都不存在卡死；新发现的可重现等待链已修复，现场窗口回调修复持续纳入回归。

旧实现对照分别在视频会话锁、后台缓存撤销／统计锁、PCM 清理、歌曲事务和持久封面会话处触发预期响应断言。扩展存储回归还验证临时封面清理／删除在原文件监视器被占用时返回，以及实际删除最终完成。Apple 回归先写入真实生产 PCM 缓存，退休后验证原缓存字节被清零，并覆盖解码器尚在创建时的取消。

最终 102 个入口与 35 个基础运行时变体全部通过；文件清理相关旧测试改为先检查逻辑撤销，再等待后台磁盘清理完成。最后补充视频失败代次门禁后，重新编译视频绑定及双加载回归，并复跑全部 5 个直接视频相关入口。最终包隔离／配置检查通过，包内文件与验证构建逐一比对。SHA-256：`9e983e0a52e4f76bedad94de0d4107c57c365fe002d2918f9a82bfc3c9dccf51`。
