# 1.0.1 翻页卡顿与视频缓存

## 翻页后点击无响应

1.0.0 修复了 PF4J 关闭后 Compose 清理回调首次加载类失败的问题。本次继续检查“发现页翻页后无法点击”和“刚打开就没有反应”的反馈，发现另一个可以独立复现的阻塞路径：

发现页和首页会并发加载封面。页面翻页后，`CoverLoader.requestSource()` 清理失效条目；页面退出也会执行 `releaseRequests()`。两者原来都会在界面线程调用 `RequestScope.close()`，同步执行 `HttpURLConnection.disconnect()`。默认 `PinnedHttpsConnection.disconnect()` 本身没有同步锁，但会调用底层 TLS Socket 的 `close()`；JDK 25 的 JSSE 关闭流程可能等待输出记录锁、排空未读记录或进行关闭协商。等待发生在 AWT/Compose 线程时，界面不能继续处理输入，后台音频和全局快捷键可能继续工作。启动时恢复账号或刷新列表也会使旧封面失效，进入同一清理路径。

`UiCancellationContractTest` 使用真实 `PinnedHttpsConnection` 和受控 Socket，模拟“网络读取和底层 Socket 关闭尚未完成，且不响应线程中断”，然后在真实 AWT 线程翻页清理旧封面。1.0.0 的 `RequestScope` 在相同测试中失败，明确报出界面线程等待断开连接；修复版在读取尚未释放时已经返回，读取释放后连接也完成关闭。测试不访问真实 CDN，也不把这个受控等待当作已捕获用户现场的 TLS 堆栈。

现在取消请求先标记失效、移除连接并取消计时任务；后台执行实际断开。请求检查会优先处理已经取消的状态，迟到的封面与播放结果不能发布。正常读取完成后的连接释放仍在读取工作线程完成。视频 Range 服务取消上游连接也采用同一方式，并将正常断开移出请求对象的锁。

每个请求各自创建的定时线程合并为两个共享定时线程，取消的任务立即从队列移除，没有任务时定时线程可以退出。视频队列读取只在请求视频后进行，避免模组启动时主动初始化宿主 PlaybackService/BASS；同一队列快照复用解析结果，避免预缓存的有效性轮询重复遍历大型歌单。

这个测试确认了一条与反馈相符的代码原因。当前运行进程的线程采样没有捕获到死锁，不能据此认定所有用户的卡顿都由同一个问题引起。1.0.0 的后台初始化、原生窗口消息钩子及卸载回归继续保留。

## 默认分辨率与选流

“音质”设置页新增默认视频分辨率：2160p、1440p、1080p、720p、480p、360p，默认 1080p。当前视频模式下修改设置会重新解析视频。播放和预缓存使用同一套选流规则，所选档位没有可用流时向下选择；不选择高于设置的流，不播放试听，也不绕过账号权限或平台拒绝。

该设置控制上游视频源；现有 D3D11 帧读取仍限制为 1280×720 后按窗口缩放，选择更高源清晰度不会改变这个绘制上限。

- Bilibili：按返回的实际清晰度降级，竖屏视频比较画面短边，同档优先 AVC，也接受宿主 FFmpeg 支持的 HEVC/AV1。1440p 没有独立的 B 站请求档位，申请至 4K 后过滤实际尺寸。优先响应中已有的普通 CDN 镜像，保留完整签名，跳过单个不符合传输策略的 URL；404/410 可以尝试同一授权响应中的下一候选，权限和风控拒绝直接停止。
- 网易云：依次请求当前档位和较低档位，可以使用服务端返回的更低清晰度；无流或不支持的档位继续降级，账号、试听和身份校验仍有效。
- QQ MV：使用 `MvUrlProxy` 的 `filetype`（10/20/30/40/50）或实际尺寸、清晰度标签选择平滑/标清/高清/全高清/超高清；未知清晰度不当作满足上限。优先合法的 `freeflow_url`，再尝试同一响应的 `url`。

实现参考了 [PiliPlus](https://github.com/bggRGjQaUbCoE/PiliPlus) 的 `video_utils.dart`、播放 URL 模型、质量选择测试和播放器缓冲配置：候选地址应按 CDN 类型区分、备用地址保留原签名、清晰度和编码分别选择、网络播放使用有限缓冲。本插件继续使用 Salt 的 mpv 和已有受限 HTTPS/Range 传输，没有复制 Flutter 界面或替换宿主播放器。

## 当前视频不能播放的原因

调查时的公开视频《崩坏：星穹铁道》EP：「无中生有」（`av117591389702977`），在旧代码中复现了 `Invalid Bilibili platform response`。官方响应的首选地址使用 MCDN 特殊端口，另一个地址同样使用特殊端口；旧代码校验第一个地址失败后直接终止，尚未尝试响应中的合法标准 HTTPS CDN。

修复后，同一视频已通过官方接口解析和一字节媒体 Range 探测。日志只记录结果、公开标题和媒体长度，不输出 Cookie、账号内容或签名 URL。这验证了解析与 CDN 访问；没有替用户重启正在运行的 Salt，也没有把远程视频的桌面画面或声音作为已验收项。

## 视频缓存

此前视频服务器的缓存预算为零，视频读取直接下载，没有进入音频已有的缓存/合并下载路径。现在视频也使用受限磁盘分段缓存，按 2 MiB 对齐块处理任意进度 Range，并预热 MP4 首尾数据。连续实际播放还会有限预读，mpv 配置约 32 MiB 的解复用缓冲和 20 秒预读。

视频模式下，后台预缓存当前视频及 Salt 实际队列的后三首；随机、循环和单曲循环沿用原生有效顺序。当前播放与预缓存共用同一媒体租约，避免播放时重复下载。没有 MV 的歌曲跳过，音频模式不预下载视频。切换队列、账号、分辨率或缓存设置会取消旧请求；已经关闭视频时停止预缓存。

音频和视频分别使用设置中的缓存上限，默认各 2 GiB，设置文字明确说明各自预算。关闭缓存保留直接流式播放；清理缓存同时清除两类分段数据，不删除账号、歌单或本地文件。缓存只保留当前运行期间的受限媒体租约，不构成离线下载功能。

## 验证

完整本地构建包含 94 个回归入口、核心策略、宿主 UI ABI 和产物检查。新增及扩展的检查覆盖：慢读取时翻页/退出仍响应、请求超时、视频首尾预热、非对齐进度读取、重复播放缓存命中、整首预缓存、预算为零、清理和撤销、慢预缓存不能卡住前台播放、默认清晰度与降级、无效首选地址后使用合法备用地址，以及当前加后三首的预缓存与设置/队列变化。

离屏视频解码、渲染和生命周期回归继续运行；真实桌面窗口、鼠标操作及屏幕帧率采样仍需显式启用，默认构建不会打开或控制用户桌面。更新包后完整退出 Salt 并重新启动，使旧加载器和已失效的界面协程退出。
